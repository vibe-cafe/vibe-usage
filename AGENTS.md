## Network Privacy Principle (highest rule, decided 2026-11-24)

This is the product's highest rule. It outranks features and convenience; where
any other rule, issue, or contributor request conflicts with it, this rule wins.
Many users reach overseas services only through a proxy, and what they care
about most is a vendor seeing their real IP together with their vendor account.

1. **Follow the user's network.** Every network request made by Vibe Usage or
   by any process it launches (the CLI, Claude Code, `agy`, `grok`, …) honors
   the proxy configuration on the user's machine: system proxy, PAC, proxy
   environment variables, TUN. A request that cannot honor it is not sent.
2. **Stricter for requests made with a vendor account.** A request made with
   the user's AI-vendor account (quota reads, usage fetches) is sent only when
   we can confirm it will leave through the user's network settings. This
   includes requests that a process we launch (Claude Code, `agy`, `grok`, …)
   makes with its own login. When the route cannot be confirmed, the request
   is not sent, and the panel says why.
3. **Proxy expected but not running: pause vendor-account requests and tell
   the user.** If the user has told us they rely on a proxy and no proxy is
   detected, the requests in point 2 pause (requests without a vendor account,
   such as npm or update checks, are not covered by this point), the panel
   shows that no proxy was detected and reading is paused, and reading resumes
   on its own once the proxy is back. Whether the user relies on a proxy is
   asked once, the first time no proxy is detected, and remembered; it is never
   guessed. Users who answer that they need no proxy connect directly as usual.
4. **Never change the user's settings.** Telemetry or non-essential traffic the
   user turned off stays off, including inside processes we launch.
5. **Only necessary requests; documented and switchable.** Every kind of
   network activity is described in the privacy notes, and every product can be
   switched off on its own.
6. **Every change answers to it, without a worse experience.** Any change that
   adds or alters network behavior states, point by point, how it meets 1–5,
   and whether the user experience gets worse. Compliance must not come at the
   cost of a worse experience: exhaust the alternatives first, and only when
   every path has been tried and none keeps both, bring the tried paths and the
   trade-offs to the maintainer for a decision. "Stop reading it" or "stop
   offering it" is not a proposal on its own. This is a required part of the
   approval request (see Architecture Approval Gate), and cross-review checks
   against it.

Scope of the promise: on our side we never route around the user's network
settings, and when unsure we do not send. Sites that the user's own proxy rules
send direct are respected. Our own server, the npm registry, and GitHub update
checks see the user's egress IP; they carry no vendor account and must be described in
the privacy notes.

Existing code does not fully comply yet. The fixes are tracked separately and
land under this principle; until then, do not widen any gap.

## Architecture Approval Gate

A GitHub issue, pull request, or feature request is a **proposal**, not approval
to change product architecture. A broad maintenance request such as "fix every
meaningful issue" authorizes triage and ordinary fixes; it does **not** waive
this gate.

Get explicit maintainer approval for the concrete design and rollout **before
editing, merging, version-bumping, publishing, or deploying** any change that
affects one or more of:

- source of truth or control-plane ownership (backend vs. local config);
- privacy/security policy, collected metadata, or precedence between settings;
- first-run defaults, onboarding questions, or opt-in/opt-out semantics;
- hostname/device/session identity, dedup keys, incremental-state keys, or reset behavior;
- cross-repository API contracts, backend storage/schema, or migrations;
- automatic update behavior across CLI, daemon, Mac, and Windows distributions.

Before requesting approval, state the current invariant, proposed invariant,
affected repositories/data/users, compatibility and migration behavior,
release ordering, and rollback plan. For a change that adds or alters network behavior,
also answer each point of the Network Privacy Principle above. Do not infer approval from issue labels,
age, detail, author confidence, or the absence of objections. A bug fix that
only restores already-documented behavior does not need a new architecture
decision; this exception does not cover a change that adds or alters network
behavior (including fixes to proxy handling), which always goes through this
gate.

**Current Vibe Usage invariant:** upload/privacy policy is backend-owned.
`sync.js` fetches `/api/usage/settings`, caches the last backend answer only for
same-server outages, and the ingest endpoint independently enforces
`usageUploadProject`. Local `config.json` contains operational client state; it
must not gain higher-priority policy controls without an explicitly approved,
cross-repository RFC. `hostname` is a stable upload identity, so changing its
meaning is also an architecture change.

Incident marker: v0.10.15 introduced local privacy precedence and new defaults
from issue #49 without architecture approval; v0.10.16 fully reverted it. Do
not reintroduce any part as a "compatibility" or "small privacy" fix without
passing this gate.

## Kiki source proposal

Kiki reports `source: 'kiki'` and displays as `Kiki`; it never falls back to
`kimi-code`. This proposal requires maintainer approval of the additive source
and compatibility-history cut, plus registration in the web application's
`USAGE_SOURCES` before publishing. The web source registry is not in this CLI
repository. Pricing continues to resolve model ids through the existing,
source-agnostic map; check normalized ids there before release.

`src/parsers/kiki.js` reuses `parseCurrentKimiRoots()` with Kiki-only model
normalization and exact cross-copy accounting/timing dedup (session + agent +
allow-listed payload + occurrence). Identical calls within a wire remain real
deltas. `$KIKI_HOME` defaults to `~/.kiki`; `VIBE_USAGE_KIKI_DIR` replaces discovery
for fixtures. A physical home owned by Kimi Code is excluded from Kiki.

`src/kiki-migration.js` protects first-upload legacy overlaps in `sync.js` after
hostname/privacy mapping. A legacy overlap is either an exact bucket key with a
changed or absent Kimi-only hash, a `kimi-code` state key sharing the same model
and half-hour window but a different project/hostname whose hash differs from
the CLI's own current Kimi snapshot, or a matching session key. The
different-coordinate arm exists because the one collector that ever reported
Kiki as `kimi-code` (Kiki's `kap-server` export, `vibe-kimi-bucket-v1`) uploaded
`project: 'unknown'` and `hostname: kiki-<stream_id>`, which the CLI can never
reproduce — matching only its own coordinates left the guard dead code. These
are conservative evidence, not proof of a mixed bucket; an unchanged genuine
Kimi-only bucket is not a signal. Other sources continue. Explicit `kikiStartAt`
is a UTC half-hour boundary: old mixed keys remain untouched, new Kiki buckets
start at the cut, straddling sessions are not re-keyed. `config set kikiStartAt
none` clears the cut at any time (the documented escape hatch for a user who
asserts no collector ran); changing to a *different* time once `kiki|` state
exists is still refused. `init` carries an existing `kikiStartAt` into the
config it rewrites (issue #142): the device flow mints a new key, the re-bound
`state.json` starts empty, and without the cut that first sync re-sent pre-cut
Kiki history as `kiki`. `planKikiMigration` also returns `withheld`
(bucket/session counts, `totalTokens`, `earliest`/`latest` ISO starts) for
everything the plan drops and `frozenBuckets`/`frozenSessions` for the
`kimi-code` rows held at their recorded hash; `sync.js` reports all of it on
stderr even in quiet/daemon runs. No cloud deletion, automatic cut,
compatibility-source upload or whole-history relabel is performed. Missing
state/changed identities and exact same-key genuine Kimi changes require user
coordination; hashes cannot reconstruct per-tool historical contributions.
Focused fixtures: `test/kiki.test.js`, `test/kiki-migration.test.js` and
`test/daemon-service.test.js`. All test data must be synthetic and home-isolated.

## Key Conventions

- **Approved 2026-09-10 — Cola source:** add `cola` to the CLI and backend source registries using the existing bucket/session schema and backend-owned privacy policy. Read `~/.cola/sessions` or `$COLA_DATA_DIR/sessions`; project comes from the session cwd basename, never a channel/scope slug. Cola 1.4.4 copies transcripts with a new header id/time but unchanged records: opt only Cola into dedup by record id + original timestamp + parent id + role + model, keep the richest usage, and attribute it to the earliest available header (stable session-id/path tie-break). Existing Pi-family dedup keys remain unchanged. Read failures protect prior upload state and suppress partial Cola uploads. No migration/reset is required. Release ordering: deploy backend source registration first, then commit the CLI support together with the Hermes fixes in the unpublished release; the maintainer publishes npm. Rollback removes Cola parsing/registration while preserving existing data.

- **Additional runtime roots** — `config roots / add-root / remove-root` manages additive data directories. Follow the [parser and fixture conventions below](#additional-runtime-roots) when extending support.

- **Pure ESM** (`"type": "module"`) — no CommonJS, no build step
- **Zero dependencies** — only Node built-ins (fs, path, os, crypto, https, readline, child_process, zlib, `node:sqlite`)
- **Incremental upload** — parsers emit a complete view of live local data, then `sync.js` diffs each item's content-hash against `~/.vibe-usage/state.json` and uploads only new/changed buckets/sessions — a quiet machine sends zero bytes. State is committed per-batch only after that batch's upload succeeds (failed batch re-sends next run); prune of dead keys (logs the parsers no longer emit) persists unconditionally and is bounded by liveness, never by age — and is scoped to sources whose parser succeeded that run, so a transient failure or an incomplete Codex cache build never evicts that tool's state into a full re-upload. Deleting `state.json` triggers a one-time full re-upload (which is exactly how `reset` re-populates remote data after deleting it). `state.json` also carries an `identity = { apiUrl, keyFingerprint }`; when the current upload target's identity doesn't match the recorded one, the state is treated as stale and the full local history is re-uploaded against the new target, so a re-bind (new `apiKey`/`apiUrl`) can't be masked by a previous account's upload state.
- **Cursor source order** — the CSV export stays primary because it resolves historical model ids (`auto`, `composer-1`, `gemini-*`, …). The dashboard events API (`/api/dashboard/get-filtered-usage-events`) is a fallback only for an empty/renamed-token CSV: on the same 9,383-event account (checked 2026-10-23) it labels 462 historical buckets as model `default`, which would both lose pricing attribution and double-count those rows as new keys. The fallback exists for X Subscription / unified accounts whose CSV comes back empty; its warning tells the user that early model names may be incomplete.
- **Parser diagnostics** — a parser may return `info` alongside buckets/sessions (currently Cursor's signed-in account label, newest event, what this run read, and since #131 its `syncedAt` / `backfill` progress). `sync.js` warns at once when the account changes or the newest event moves backwards (`reportParserInfoChanges()`), but writes the info into `state.parserMeta` (`recordParserInfos()`) only after every item that source changed in the run has been committed, in the same `saveState()` as the last of those hashes; a source with nothing to send records it right away. The info is not only diagnostics: Cursor's events fallback asks only for events newer than the recorded `latestTokenAt`, so when `sync.js` wrote it before uploading, any save (the prune save, another source's batch) persisted it and a failed or killed upload made the retry skip the events the server never got. "Committed" follows the hash rule: a 200 whose `dropped.unknownSources` names the source leaves its hashes and info uncommitted for a retry; items dropped for other reasons are committed. Coverage: `test/sync-parser-meta.test.js` (Cursor fallback retry after a failed or killed upload; several sources against the prune save, another source's batch save, nothing to send, and `dropped.unknownSources`). `status` prints the recorded info. It is local-only: never uploaded, never part of a bucket/session key, and dropped when `state.json` is re-bound to another upload account.
- **Hidden-project identity** — parsers aggregate before the backend-provided privacy setting is applied. When the fetched `uploadProject=false`, `sync.js` replaces project names with `unknown` and must re-aggregate buckets before hashing/upload so formerly distinct projects that now share a server key are summed instead of overwriting one another. This is enforcement of backend policy, not a local setting.
- **Cost-accounting invariant** — parsers report token counts plus only price-changing model dimensions (for example Codex `service_tier`). Never collect, persist, or encode an account funding path such as ChatGPT subscription, API billing, credits, or bundled quota. The backend always estimates `tokens × provider-published model/service-tier rate`; funding never changes that value. v0.10.18's `#billing=api` / `#billing=subscription` experiment violated this invariant and v0.10.19 removed it. Do not reintroduce it as billing accuracy, plan detection, or incremental cost.
- **Codex Ultrafast cut (2026-11-18)** — see the approval above and `src/codex-ultrafast.js`. The cut is server state: do not cache it in `config.json` or `state.json`, do not add a `config set` for it, and do not make a sync without a confirmed answer fall back to the merged format. `parsers/codex.js` must keep Ultrafast usage undecorated in every cache layer (summary, tail, segment group) and apply the cut only in `mergeFileResults()`.
- **Codex parser cache** — unlike the other stateless parsers, Codex keeps versioned, disposable derived data under `~/.vibe-usage/cache/codex/`. This cache is never authoritative: any miss, corruption, unsafe append, parser-algorithm bump, or write failure falls back to raw logs. Keep it separate from `state.json`; `reset` clears upload state but retains the parser cache so it can re-upload without re-reading every rollout. **Warm lookups (2026-11-19).** A warm sync on the maintainer's Mac (three homes, 25,628 rollouts, 11,500 sessions shared between homes) read no rollout but opened 56,862 cache entries (290 MB) and made 95,868 `existsSync()` calls: 3.24 s on Node 24. Two of those reads were for nothing and are gone: (1) `startingCache()` stops after step 1 when our own entry for exactly the file state has a header and a replay index but no summary -- every member of a shared session, whose summary is on the group's entry. Steps 2 and 3 found nothing to use there (step 3 prefers our header and index; a member needs no file summary) and cost 23,957 tail lookups and 20,222 older entries (102 MB) read and discarded per sync. What this gives up outside that case costs one rollout read, never a different result: an older summary for that exact state (normally none is usable -- our entry got its index from the rollout, a twin or an older entry whose summary was not), and the tail of a file that has an index but no longer needs one. (2) Entries are read without `existsSync()` first; a missing or unreadable entry is a miss either way. The group summaries an older version left (on that Mac 9,882 of 11,500 groups, plus the only entry of 490 rollouts) are still read from the older location every sync and deliberately not copied into `v7/`: the copy would save ~60 ms per sync (the failed `v7/` lookups) for ~1 s and ~59 MB of writes once, and would stamp algorithm-6 output as algorithm 7. So the older directory is still in use: deleting it is safe for the numbers but makes those groups merge again over several syncs. Measured on a copy of that cache, against `98c3a90`, 7 runs each, Node 24 / Node 22: warm three homes 3.24 / 3.34 s → 2.14 / 2.32 s, the same with a growing rollout 3.29 / 3.33 s → 2.18 / 2.35 s, `~/.codex` only 0.37 / 0.38 s → 0.36 / 0.37 s; cold (cache files not in the page cache, fresh copy, 2 runs) 9.44 / 9.44 s → 4.72 / 5.08 s; 37,130 entries (190 MB) and 452 `existsSync()` calls per warm sync. Outputs byte-identical to `98c3a90` in every case. Coverage: `test/codex-shared-copies.test.js` (a warm sync looks up no older entry and no tail for the copies of a shared session). **Manifest (2026-11-20).** Each home's `v7/` also holds `manifest.v1` (`loadCodexManifest()` / `saveCodexManifest()` in `codex-cache.js`): per rollout and per duplicate-session group, what the lookup found last time for one exact stat signature -- the header, the replay index without `tokenTimes` / `tokenFingerprints` / `taskBoundaries` (a "slim" index; of it the record keeps only what the header and path do not already say, `compactManifestIndex()` / `expandManifestIndex()`), the summary, `copyOf`, `lastAuditedAt` -- and `src`, the algorithm version of the entry it stands for. A warm sync reads the manifests instead of the entries. Rules: (1) A record is used only for exactly its stat signature, and only where it stands for a stop of the lookup: this version's summary, or (a file) this version's header and index; an older version's entry only whole and only from version 6 (`olderEntryRecordable()`), under `olderSummaryAccepted()` and `summaryMatchesCut()`, the rules for reading it from the older location. A version-5 entry (taken only on a Magpie-free machine) is neither recorded nor served from an older manifest, so those rollouts take exactly the lookup they take without one: served from the manifest, its index outlived a version-7 entry that a still-running 0.15.x audit rebuilt for the same file state, and a new fork was checked against it (GPT-6.2-Astra review, 2026-11-20; none on the maintainer's Mac). Anything else is looked up in the entries as before. (2) The manifest is never the source of a write: before an entry is rewritten (`updateFileCache()`) a slim index is filled -- from this version's entry for the same file state first, whatever the record was written from, then from the older entry it stands for, the order the lookup takes (`fillFullIndex()`; an older entry's index can itself be one an earlier algorithm computed, and a still-running 0.15.x may have rebuilt this version's entry since) -- or dropped, and an index copied from a hard-linked or decompressed twin is filled first. (3) Full indexes are read only to compute the replay boundary of a fork or sub-agent whose parent session is known, and not when its record says its summary was checked against exactly the parent's current state (`boundaryParent`: the parent representative's path, its stat signature and a digest of the replay index used for it, `replayIndexDigest()`; the boundary is a function of the two indexes). The digest is not optional: one file can be indexed differently -- an algorithm-5 entry, taken whole on a Magpie-free machine, fingerprints durable usage records without their response id, and gives way to an index built by this version once Magpie becomes active or the cut moves, while the parent's file stays the same (GPT-6.2-Astra review, 2026-11-20: a fork kept counting the copied parent history after `cb0b520` had corrected it). Records of sessions some fork or sub-agent names as parent carry the digest; the state is computed again from the index actually used once it is filled from its entry. It is recorded only once the summary has been checked or rebuilt against it -- never for a session left for the next run. Not named `*.json`, so nothing that walks the entries takes it for one; collectors of algorithm 7 that predate it (0.15.x) ignore it, and what they write to the entries only makes records stop matching. A sign-in answer from ② is final; from ① it falls through to ② / ③ and is reported as `agyLoginRequired`, after which the provider skips ① until agy's own store changes or the binary changes.
  - **Children.** Every child environment excludes `BIGMODEL_API_KEY` and `Z_AI_API_KEY`. `agy` children (`runAntigravityCommand`) get `AGY_CLI_DISABLE_AUTO_UPDATE=true` (lowercase; set case-insensitively, overriding an inherited value; never written to any file) and, in their temporary cwd, do-nothing launchers first on `PATH` — `open`, `xdg-open` and `BROWSER` on Unix, `rundll32.bat` on Windows — that only leave a mark: in print mode a failed silent sign-in makes agy exec its browser launcher through `PATH` (CodexBar #4441 / #4451, verified with agy 1.3.3), and the mark ends the run as `LoginRequired` within 100 ms. A launcher agy reaches without `PATH` is not covered; the sign-in block keeps that to one tab. Login text in agy's stdout/stderr (`agyRequiresLogin`) also ends it. Our desktop engine closes stdin, sets `ANTIGRAVITY_VSCODE_HOST=1` (suppresses browser login) and points both `--gemini_dir` and `ANTIGRAVITY_GEMINI_DIR` at its temporary directory; only the `ANTIGRAVITY_OPEN_URL:` marker or a Google OAuth URL is a login signal there. Loopback requests use a fresh `http` / `https` agent so `NODE_USE_ENV_PROXY` and the CLI's own tunnel never route `127.0.0.1` through a proxy. Every owned process tree and temporary directory is cleaned up. Vibe never reads or refreshes AGY's sign-in; it reads a running desktop's loopback CSRF token from the process list (the legacy `.pb` parser already did), which is not an OAuth credential and goes only to that process's own ports.
- **Quota `emptyReason` (2026-09-27)** — a quota result may carry `emptyReason` (`limitReached`, `noWindow`, `notEntitled`, `sessionWithoutPlanLimits`), additive within schema v1 and validated against `QUOTA_EMPTY_REASONS`. It exists so a client renders *why* there was no window instead of parsing `message` prose; the desktop clients' `EmptyReason` enums mirror the same vocabulary. OpenCode Go emits `notEntitled` on HTTP 403 (valid key, no Go plan).
- **Kimi quota credential resolution (2026-09-26)** — the provider reads the first login that exists among `$KIMI_CODE_HOME` / `~/.kimi-code` (kimi-code 2.x — the same home `kimi-roots.js` uses) and `$KIMI_SHARE_DIR` / `~/.kimi` (kimi-cli 1.x, legacy); with no login anywhere it returns the 2.x path, because that is where the installed CLI now logs in and where a later rotation must land. Resolution is by *presence*, and the 2.x home outranks the legacy one, so a stale `KIMI_SHARE_DIR` cannot shadow the current CLI login. Do not narrow this back to `$KIMI_SHARE_DIR || ~/.kimi` — every 2.x user then gets `missing_credentials` while their token tables sync fine (issue #112; reproduced live 2026-09-26).
- **Approved 2026-09-19 — quota meter layout** — schema-v1 meter arrays put generic time windows first from shortest to longest; provider-specific/model/feature meters keep their relative order afterward. Exact generic aliases are compacted for display (`Daily` → `1d`, `Weekly` / `1w` → `7d`) and exact daily/weekly durations may be filled when the provider omitted them. The CLI applies this to live and cached results; Mac and Windows repeat the ordering defensively for older CLI snapshots. No backend, upload, credential, config, or cache-format migration is involved.- **Say the size before sending it** — `sync.js` prints the pending bucket/session counts and batch count before the upload loop, a remaining-time estimate inside the per-batch progress line, and the compressed bytes plus elapsed time at the end. The estimate is extrapolated only from batches that already finished (`estimateRemainingSeconds()` returns `null` until then): a first-sync backlog and a steady-state trickle differ by orders of magnitude, so any a-priori rate would be wrong for one of them. All three lines are `!quiet`-gated — the desktop apps parse piped stdout.
- **No silent minutes before the first result** — `sync.js` draws one redrawn status line (`liveStatus()` in `output.js`) while it fetches backend settings and while the parsers scan/index local logs (`正在读取上传设置 · 已用时 0s` → `正在扫描本地日志 34/35 · 已用时 5s`, ticked every 5s). A cold Codex index build, a long Cursor event history, or a settings endpoint re-trying through its timeouts otherwise leaves the sync header as the last visible line for minutes — the exact way a slow sync reads as a hang. The line is **TTY-only for the same reason as `hint()`** (the Mac and Windows apps parse piped stdout as the result text) and is erased before the parser result block prints, so only interactive users see it. `VIBE_USAGE_FORCE_PROGRESS=1` forces it on for tests and `VIBE_USAGE_PROGRESS_INTERVAL_MS` overrides the redraw interval. Coverage: `test/sync.test.js` (`silent sync phases report live status only on a TTY`).
- **A slow network parser uploads last, not instead** (issue #131, approved 2026-11-04 — see above) — `runSync` starts the `DEFERRABLE_SOURCES` parsers (currently `cursor`, whose whole-account export took 137s on a heavy account) outside the parser pool. If one is still running when the local parsers finish plus a 5s grace (`VIBE_USAGE_DEFERRED_GRACE_MS`, test hook), the finished tools go through a full diff/prune/upload pass first and the slow source gets its own pass afterwards; otherwise everything stays one pass with one summary, as before. Each pass prunes only its own sources and commits state per batch, so keys, values and state are what a single pass would produce — only the order changes. Both passes share the one upload client and therefore one `syncId` per `runSync`; each pass ends with its own final batch, which the backend only uses to refresh its upload-client inventory. If the second pass fails, the failure line counts everything either pass delivered, sessions included (`部分完成（已上传 N buckets · M sessions）`) — on a 401 too, as one stderr line `部分完成（…）: API Key 无效…`, because the Windows app shows the last error line of stderr — and the process exits 1. Coverage: `test/sync-deferred.test.js` (slow/fast Cursor, quiet mode, per-pass pruning with existing state, first- or second-pass failure, sessions-only first pass, an interrupted multi-batch second pass resuming, re-bound identity and the Kiki guard across passes).
- **`doctor --json` is a contract (2026-11-09)** — every field and code it can emit is listed in `docs/doctor-json.md`, and `test/doctor.test.js` fails when a code in `WARNING_CODES`, `SYNC_FAILURE_CODES` or `PROBE_ERRORS` (or a documented field) is missing there. Adding a field or code is fine within schemaVersion 1; renaming, removing or changing the meaning of one needs a schemaVersion bump coordinated with both apps. Anything new must stay inside the whitelist rules above — never a path, name, hostname, handle, raw message or key.
- **Warning codes (2026-11-09)** — `warning-codes.js` maps every parser warning (and every error a parser throws) to one code of a closed vocabulary (`read_failed`, `dir_unreadable`, `unsupported_format`, `cursor_token_encrypted`, …) by the fixed wording our own code writes around the embedded raw parts. Only codes and counts go into the sync history and `doctor`; stderr keeps the original text. An unrecognized warning becomes `other` (an unrecognized thrown error `parser_error`), so a new template can lose precision but never leak text. When you add or reword a warning, add a rule and a case to `test/warning-codes.test.js` (it lists every template as of 2026-11-09 — about 80 warning sites in 26 parser and roots files — plus the thrown errors that reach `sync.js`).
- **Parser warnings are never filtered** — `sync.js` writes every parser warning to stderr, including quiet (daemon) runs, because the daemon log is the only trail a background failure leaves. A quiet-mode filter for Cursor's fetch soft-skip made a permanently failing export indistinguishable from a healthy one: empty `daemon.log`, `status` still listing the tool as installed, and zero data for months. Keep transient/permanent distinctions in the *message*, not in whether it is printed.
- **Output style** — user-facing text is Chinese (colored via `output.js` helpers: `success` / `failure` / `warn` / `arrow` / `link`). Dashboard URLs use OSC 8 hyperlinks so terminals that support it (iTerm2, Warp, VSCode, Kitty, Terminal.app 14+) render them as clickable. Raw pass-through from external tools (parser errors, `systemctl` / `launchctl` output, daemon loop timestamps) is kept in English and dimmed so it's visually de-emphasized. `init` prints a big ASCII logo; other commands print a compact one-line header (`bigHeader()` / `smallHeader()` from `output.js`).
- **CLI compatibility** — keep the documented legacy aliases `--key` (for `--manual-key`), `--daemon` (for `daemon`), and `reset --host` (for `reset --local`). The bare invocation remains init-or-sync, and since v0.10.25 the only command we advertise; every other subcommand stays supported. `--no-daemon` and `help --all` are public flags. Old spellings (`sync`, `daemon install`, the aliases above) print a one-line `hint()` pointing at the simpler form — **TTY-only**: the Mac and Windows apps read the CLI's piped stdout as the sync result / error text, so never print hints to a pipe. Do not preserve arbitrary unknown-command fallthrough; it was never a public command and can turn typos into unintended side effects.

## Additional Runtime Roots

`src/extra-roots.js` owns `EXTRA_ROOT_SOURCES`, `validateExtraRoot()`,
`extraRootList()`, and the source-specific layout resolvers, including
`grokSessionsDir()`, `antigravityConversationDirs()`, and `piSessionsDir()`.
Hermes homes are checked with `inspectHermesHome()` in `hermes-roots.js`
(readable `state.db` or `profiles/<name>/state.db` under the configured path).
The currently supported source ids are `antigravity`, `claude-code`, `codex`, `grok`,
`opencode`, `pi-coding-agent`, and `hermes`.

- **Config routing:** `config roots` lists `config.extraRoots` as JSON;
  `config add-root <source> <path>` validates and persists a normalized path;
  `config remove-root <source> <path>` removes it. `sync.js` passes
  `extraRoots: extraRootList(config.extraRoots?.[source])` to each parser.
  The config key must exactly match its parser/source id (`pi-coding-agent`,
  not `pi`).
- **Additive discovery:** keep each tool's default store and any legacy
  `codexExtraHome` configuration. Extra roots must not replace or mask them.
- **Parser result:** merge roots and de-duplicate overlapping paths or copied
  records inside the parser before returning buckets and sessions. The dedup
  identity is the source's own stable **record identity** — session id and/or
  message id — never the database or file path alone. Two paths holding the same
  session (a migrated or copied home, a backup directory, a mirrored profile)
  must count it once, and when the copies disagree keep the most complete one,
  the earliest root winning a tie. Path identity remains as the first pass that
  stops one physical file being read twice; it cannot see a second file holding
  the same records. Per source: OpenCode session id + message id, grok session
  id, pi message id, claude-code logical session id + request id, codex
  cross-file copy suppression, hermes session id + `(session, role, timestamp)`
  message triple. Path-only dedup is not sufficient — it silently double-counts
  every token of a copied store while the timing stream, grouped by session
  hash, still reports a single session, so the two tracks disagree (issue #118).
- **Read failures:** a configured root that is missing, unreadable, or no longer
  resolves must produce `skipped: true` with a warning, never an empty success.
  This prevents `sync.js` from pruning that source's prior incremental state.
- **Fixture isolation:** overrides should isolate normal machine discovery.
  Grok ignores configured roots when `VIBE_USAGE_GROK_SESSIONS` is set. Pi
  currently still validates and appends explicit `extraRoots` when
  `VIBE_USAGE_PI_SESSION_DIRS` is set, so its tests must also pass only temporary
  extra roots. Do not assume the override alone isolates those tests.

- **Claude / OpenCode roots:** the config id is `claude-code`, never `claude`. Claude keeps its existing physical-session/request-copy selection; validate explicit roots on every run and mark the source skipped if projects/transcripts disappear. OpenCode discovery and parsing share `opencode-roots.js`: SQLite wins independently within each root, including empty databases; JSON is used only where no database exists. Read failures suppress partial OpenCode outputs and protect state.
- OpenCode merges raw accounting/timing records before aggregation. Deduplicate copied stores by session id + message id, keeping the copy with the largest token payload (default root wins ties); anonymous ids stay scoped to their physical store. Canonical paths remove symlink overlap. Keep existing token semantics and top-level model/project precedence; nested `model.modelID` only fills an absent model field; project derivation is unchanged. No reset or backend change is needed. `VIBE_USAGE_OPENCODE_DIRS` replaces default discovery; explicit test `extraRoots` remain additive, like Claude.
- **OpenCode 2.x store (2026-09-26, issue #114)** — 2.x writes the event-sourced `session_message` projection instead of the legacy `message` table (`seq`-ordered `id, session_id, type, data, time_created`), and its session table is renamed to `session_v2` (`session` is the pre-split 1.18-era name; a fresh 2.x database has no `message`/`part` tables at all) — join `session_v2` when it exists, else `session`. Assistant rows carry `type='assistant'`, `data.model.id`, `data.tokens` (per-message deltas; the `session_v2.tokens_*` columns are their sum, so never add both), and no project path, so their project falls back to the session row's `directory`; `time_created` is ms epoch (prefer `data.time.created`, fall back to the column). Read every shape present in one database, legacy table first, and merge copies by session id + message id: a 2.x upgrade that keeps both representations must not double count, and legacy-first ordering keeps the project label earlier uploads already used. V2 rows are new uploads, so their directory-derived project cannot rename anything. A database with neither table returns `不认识的表结构` (naming the path) and skips the source; the pre-2.x query failed on `no such table: message` for every 2.x user, which silently uploaded nothing.
- **OpenCode cache writes are a priced dimension (2026-09-26)** — `tokens.cache.write` maps to `cacheCreation5mTokens`, the same rule as CodeArts Agent (identical store layout, one untyped total, no per-TTL breakdown). Emitting only input/output/cache-read/reasoning under-billed every Anthropic run through OpenCode at the 1.25x cache-write tier (69.3M dropped cache-write tokens on the maintainer's own store). `inputTokens` stays uncached-only, and existing buckets re-upload under the same key, so the correction replaces rather than adds.
- Validation for #81 includes a read-only comparison against an actual default OpenCode store: buckets and sessions matched pre-change main exactly. Synthetic SQLite/JSON stores cover cross-root copying, model fallback, failures, and the full config → detection → parser route. No production upload was performed.

- **Hermes roots (2026-10-07, PR #118):** `hermes` is an extra-root source driven by `extraRoots.hermes`; `inspectHermesHome()` in `hermes-roots.js` validates a configured home (a readable `state.db`, or at least one `profiles/<name>/state.db`), and a configured home that is missing or unreadable yields `skipped: true` with a warning rather than an empty success. Default discovery (`~/.hermes`, Windows `LOCALAPPDATA/hermes`) and `HERMES_HOME` stay additive and are never masked. Each profile is an independent store, and `profile` — `'default'` for `<home>/state.db`, else the directory name under `profiles/` — is the project label, which a copied home preserves. The parser applies the record-identity rule above: the `sessions` table holds cumulative per-session totals, so it keeps the richest row per session `id`, and the `messages` timing stream is deduped by `(session_id, role, timestamp)`. Verifying `state.db` by realpath only stops one file being read twice; a *copy* at a second path is a different path and is caught by the record rule instead. `HERMES_HOME` was already in `PRESERVED_SERVICE_ENV`, and extra roots live in `config.json`, which the daemon reads through `runSync`, so this needs no service-env change. Coverage: `test/hermes.test.js` (copied store, richest-copy-wins, symlinked root) and `test/hermes-discovery.test.js` (additive discovery, skip-on-missing).

## Architecture: Two-Track Data Model

Every parser produces two parallel data streams:

### Track 1: Token Buckets
Per-message token usage aggregated into 30-minute windows via `aggregateToBuckets()`.

```js
{ source, model, project, bucketStart, inputTokens, outputTokens, cachedInputTokens, reasoningOutputTokens, cacheCreation5mTokens, cacheCreation1hTokens, totalTokens }
```

**Cache writes are a priced dimension, not input** (2026-09-16). Anthropic bills
prompt-cache writes at **1.25x** (5-minute TTL) and **2x** (1-hour TTL) the base
input rate, so `cacheCreation5mTokens` / `cacheCreation1hTokens` travel as their
own columns instead of being folded into `inputTokens` the way `claude-code` did
before. Folding them in under-billed real Claude buckets by 13-33% depending on
the model. Rules for a parser that emits them:

- Only split when the log actually distinguishes the two TTLs. An
  unexplained remainder (a total with no breakdown, or a breakdown that sums to
  less than the total) goes to the **5m** bucket — the cheaper multiplier, so a
  partial log can only under-state cost.
- `totalTokens` still includes them, so the number is bit-identical to what the
  same log produced when they lived inside `inputTokens`; the server uses that
  field only as a `> 0` liveness filter and no bucket may silently drop out.
- Parsers that cannot tell the TTLs apart (the Pi family, Cline SDK, DSH, Cindy)
  keep folding cache writes into `inputTokens` and leave both new fields at 0.
  That is a known remaining divergence, not an invariant.
- `state.js` `bucketHash()` covers both fields, so a pure 5m↔1h reclassification
  still re-uploads.

**Fast mode is a service tier.** Claude Code records `message.usage.speed`
(`'standard'` | `'fast'`); `'fast'` doubles Opus 5 / Opus 4.8 input and output
rates. The parser appends a `-fast` marker to the model id, which the server's
pricing map resolves through `TIER_MARKER_SUFFIX` → `tiers.priority`. Models
with no published priority tier fall back to their base rate, so the marker is
safe to append unconditionally.

### Track 2: Sessions
Timing events fed to `extractSessions()` for interaction metadata.

```js
// Input event shape:
{ sessionId, source, project, timestamp: Date, role: 'user' | 'assistant' }

// Output session shape:
{ source, project, sessionHash, firstMessageAt, lastMessageAt, durationSeconds, activeSeconds, messageCount, userMessageCount, userPromptHours }
```

`activeSeconds` = sum of turn durations (user prompt to last assistant message before next user prompt).

## Adding a New Parser

1. Create `src/parsers/<tool-id>.js` exporting `async function parse()` returning `{ buckets: [], sessions: [] }`
2. Register in `src/parsers/index.js` — import + add to `parsers` object
3. Add tool entry in `src/tools.js` — `{ name, id, dataDir }` (alphabetical by id)
4. Update `README.md` supported tools table
5. **Backend**: append the source to `USAGE_SOURCES` in `vibe-cafe/apps/web/src/lib/usage-sources.ts` (ingest filter and `/usage` chip list both derive from it). Release ordering between vibe-usage publish and vibe-cafe deploy is no longer load-bearing — the ingest endpoint **soft-drops** unknown sources (returns them in `dropped: { buckets, unknownSources }` instead of 400ing the batch) so other parsers' data still lands. Until the source is registered server-side, `sync.js` prints a dim "X buckets dropped (服务端未收录的 source: …)" line.
6. **Check every model id the parser can emit against the pricing map before shipping.** Server-side pricing is source-agnostic: it matches on the model string alone. From a `vibe-cafe` checkout run `cd packages/model-pricing && bun -e "import { getModelMatchInfo } from './src/pricing'; console.log(getModelMatchInfo('<id>'))"` for each id (routing tiers, vendor-internal codes, pseudo-models). Anything that matches a price it should not be billed at must be namespaced with the tool prefix — Qoder's bare `auto` matched the Cursor `auto` entry and was billed at Cursor's rate until PR #83 renamed it `qoder-auto`.
7. Before the first release, verify against a real local store, not only fixtures: sum the raw rows independently (a SQL `GROUP BY` half-hour bucket, or a one-off script over the JSONL) and compare with the parser's buckets number for number. Third-party trackers' claims about a tool's on-disk format (e.g. "the IDE stopped writing `token_info`") are dated observations, not facts — run one real session on the current build and read the file yourself.

Parser pattern:
- Read local log files from the tool's data directory
- Extract per-message token entries → `aggregateToBuckets(entries)`
- Extract user/assistant timing events → `extractSessions(events)`
- Handle missing/corrupt files gracefully (try/catch, skip bad lines)

Pi-compatible JSONL parsers (`pi-coding-agent.js`, `craft-agent.js`, `omp.js`):
- Use `parsePiSessionJsonl()` instead of duplicating filesystem/message parsing.
- Fold `usage.cacheWrite` into input tokens and keep `cacheRead` separate. OMP/Pi `usage.output` already includes reasoning, so subtract reasoning from output before storing it in `reasoningOutputTokens`. Pi's `Usage` type spells that field `reasoning`; the older `reasoningTokens` spelling stays accepted as a fallback.
- Deduplicate stable message ids across copied/profile stores. Any directory read failure returns `skipped` so incremental state is not pruned.

SQLite-backed parsers (alma, cindy, cursor, dimagent, hermes, kiro, mcode, mimocode, opencode, zcode):
- Use `queryDbJson(dbPath, sql)` from `src/parsers/sqlite.js` — never shell out to `sqlite3` directly. It prefers Node's built-in `node:sqlite` (`DatabaseSync`, opened read-only; Node ≥ 22.5, works on Windows with no extra binary) and falls back to the `sqlite3` CLI on older Node.
- Rows come back as plain objects (`{ column: value }`), same shape as `sqlite3 -json` — INTEGER → number, TEXT → string, JSON via `json_extract` → string.
- If neither `node:sqlite` nor the CLI is available the helper throws an `ENOENT`-flavored error; catch it and rethrow `'sqlite3 CLI not found. Install sqlite3 (or use Node >= 22.5) to sync X data.'` so the user gets a hint.
- For DBs the source app holds a write lock on (Cursor, Kiro), use `queryDbJsonSnapshotOnLock()`. Cindy always uses `queryDbJsonSnapshot()` because a clean WAL-mode database may need SQLite to initialize shared-memory metadata; writable access is confined to the disposable DB/WAL/SHM copy, while the source stays untouched.
- Alma reads only `usage_records` token fields plus workspace names. Its ledger represents assistant responses only, so return buckets with `sessions: []` instead of reading chat records to infer timing.
- mcode reads only `local_runtime_token_usage` allow-listed token fields and session `workspace_dir` / `project_workspace_dir`; `raw`, message tables, and JSON payload columns are never selected. Its WAL database is read through a disposable snapshot-on-lock path, and schema/read failures return `skipped` to protect incremental state. It reads **every store the CLI can write to**, not just `~/.minimax`: `$MINIMAX_DATA_DIR` / `$MAVIS_DATA_DIR` (the CLI's own relocation variables, and `MCODE_HOME`), plus `~/.minimax-<profile>` per profile and the pre-npm `~/.minimax-code` / pre-rename `~/.mavis` homes, deduplicated by physical file and by ledger-row identity so a compat symlink or a copied migration tree cannot double-count. A broken *extra* store is reported as a warning and does not blank the live one; only the primary store keeps the `skipped` behavior. Fixture overrides: `VIBE_USAGE_MCODE_DB` or `MCODE_HOME`.
- Cindy reads only `daily_model_usage` across both regional user-data roots and every per-owner DB. Claude Code rows are excluded because Cindy's SDK already writes normal `~/.claude` transcripts; merge Codex/Pi rows into their existing parser/source, sum currency rows, fold `cache_create_tokens` into input, and add no sessions. Never select `messages`, credentials, costs, or owner ids.
- DimAgent (`dimagent.js` + `dimagent-rust.js`, 2026-11-20) is one source for both generations. The legacy TypeScript store (`getDimAgentDbPath()`, `~/.dimcode/v2/dimcode.sqlite`) keeps its `usage_ledger` reading unchanged. Rust Dim (`dima` alpha and later, arcships/dim `crates/dim-cli` `default_home()`) keeps `<home>/rust/dimcode.sqlite`; `getDimAgentRustDbPaths()` reads `$DIMCODE_HOME`, `~/.dimcode-alpha`, `~/.dimcode` and `~/.dim` (fixtures: `VIBE_USAGE_DIMAGENT_RUST_DBS`; setting only `VIBE_USAGE_DIMAGENT_DB` reads no Rust store). The parser resolves filesystem aliases before reading and accepts only Timeline rows whose session is visible in that database. Dim deletes session rows before cleaning up events in batches. For `model/usage`, `promptTokens` includes cache reads and writes, and `completionTokens` includes reasoning. The parser splits out both caches and reasoning, using `cacheCreation5mTokens` for untyped writes. Compaction uses the counters from `context/compaction` `diagnostics.modelUsage`. Model and tier come from the same request's `model/call`, the last preceding `context/configured` on that branch, or the session configuration, in that order. Rust Dim's bare `auto` becomes `dimagent-auto`. The parser appends known price-changing OpenAI or OpenAI-compatible service tiers. Token events count once by event id across forks and homes, attributed to the earliest visible session. Timing on a fork's `main` starts after its last `session/forked` marker. Other branches use local sequence numbers. Imported legacy history (`migration:legacy-import` tag, import-instant times, no usage) adds no timing; the legacy store already accounts for it. Prompts are applied `input/message` events with `data.user`. A completed `step/model-output-end` supplies timing when that request has no `model/usage` event. Member Sessions (`leader_session_id`) fold into their root as agent activity, and orphan or cyclic leader chains leave each session independent. Sessions without a human prompt emit no session. Each store is read independently. Read failures set `skipped` to protect state, and the other stores still upload. Missing required columns use the `unsupported_format` warning code. Auxiliary-model calls (titles, image understanding) record usage only in tracing logs and are not counted. Coverage: `test/dimagent.test.js` (legacy, unchanged) and `test/dimagent-rust.test.js`.

Qoder parsers (`qoder.js`, two editions via `../qoder-roots.js`):
- Source `qoder` (qoder.com) and `qoder-cn` (qoder.com.cn) are separate accounts, billing and data dirs; never merge them. Network-fetch parsers (the Cursor exception):
- **Rolling 7 days (issue #131, approved 2026-11-04 — see above).** Three paths, each run once per sync, each owning its own range: (1) the recent CSV, `[W, now]` with `W = roundToHalfHour(now − 7 days)`, keeps windows starting at or after `W` (plus the existing 24h–7d stale-gap probe); (2) the events fallback below, only when that recent CSV is empty or unusable, unchanged and **not** limited to `W` — an account whose CSV is always empty may have events older than `W` after the collector was off; (3) history blocks `[before − 7 days, before − 1 ms]` covering `[until, before)` (`planBackfill()`). One source per half-hour window: a window with any CSV row is built from the CSV alone and the fallback's events for it are dropped, never added. The export filters `startDate` / `endDate` in **milliseconds**, both ends inclusive (verified row for row against the whole export on the maintainer's account, 2026-11-04); seconds silently return nothing, so the ms form is pinned by tests. On a Cursor account switch the old account's times are dropped before any path reads them: the events fallback used to filter the new account's events by the old account's newest time and lost everything before it. An empty recent CSV with a recognized header is an ordinary idle week: when the fallback finds nothing either, no warning is printed, and `sync.js` no longer warns when the counts drop to zero. Every result carries `skipped: true` and `info.syncedAt`; a recent-CSV request failure returns no info, so the recorded progress stands. Coverage: `test/cursor.test.js` (plan, recent window equals the whole export from `W` on, first-run blocks and their boundaries, 40s budget across runs, a failing block, the 6-day gap, fallback events older than `W`, one source per window, idle sync, account switch) and `test/cursor-rolling.test.js` (multi-run sync whose server table equals one whole export).
- Cursor stores no usage locally — only the token Cursor itself wrote to `state.vscdb`. The parser reads that existing value via `queryDbJson()` (read-only, never refreshes or writes it), then GETs a CSV from `cursor.com`. No login, OAuth, account switch, browser cookie, Keychain, or unify flow is involved. If the CSV is empty, has an unknown header, or has no token counters, it falls back to the dashboard's paginated events API, bounded to events after `previousInfo.latestEventAt` (or the last seven days on a first run) so historical rows the events API mislabels as `default` are never re-added. Two rules keep each event counted once (issue #131 follow-up): (1) every half-hour window that gains a new token event is rebuilt from all of its events — the request reaches two hours before the previous newest event, since `roundToHalfHour()` can start a window up to 90 minutes before its events on a DST fall-back night — because uploading only the new events sent a smaller value under the same key (20 replacing 10 + 20), which the server's larger-total guard cannot undo; windows without a new event are not resent; the known cost is that on the run where the CSV first comes back empty, a rebuilt window can include events the CSV already uploaded under another model name, which then count twice (at most one window per usable→empty switch); (2) a fallback run that finds no new event, or whose events request soft-fails, carries the previous `latestEventAt` / `latestTokenAt` forward in its `info` (same Cursor account only), because `sync.js` replaces the recorded info whole and an info without them sent the next run back to "the last seven days", re-reporting `auto` history as `default`. Coverage: `test/cursor.test.js` (window rebuild, kept anchor, DST under `TZ=America/New_York`) and `test/sync-parser-meta.test.js` (both counterexamples end to end). A usable CSV whose newest event is 24h–7d old also gets a one-hour-overlapped events probe, and only events newer than the CSV's newest row are merged; `fallbackLatestAt` in parser info suppresses the repeat warning for the same gap.
- Always wrap network calls with `AbortSignal.timeout(...)` so a single hung host can't stall the whole sync (sync.js catches throws per-parser but cannot interrupt a hanging await).
- Size that timeout for the **slowest request**, not the median one. cursor.com builds the export in time proportional to the rows it returns (a heavy month measured 69–80s), so its latency scales with the user's usage: a too-short default does not fail intermittently, it locks heavy users out of every single sync. 10s (v0.7.11) and 30s (#72) both did this; the default is now 120s, overridable via `VIBE_USAGE_CURSOR_FETCH_TIMEOUT_MS`.
- Mark transient/network errors with `err.skip = true` and return `{ buckets: [], sessions: [], skipped: true }` so the parser stays quiet without letting `sync.js` prune that source's incremental state. Only auth/permanent errors should bubble up.
- **Treat the export's header as an external contract.** Require `Date`, `Model` and at least one token column; on a mismatch return `skipped: true` with a warning naming the observed header. Without this check a renamed column parsed every row as zero tokens, produced an empty upload, and let `sync.js` prune Cursor's state as if the account had gone quiet (silent, months-long). Same fail-closed rule as the network path.
- **An encrypted token is skipped, never decrypted (issue [#144](https://github.com/vibe-cafe/vibe-usage/issues/144), decided 2026-11-07 by the maintainer, Hogan).** Cursor 3.27+, behind its remote flag `cursor_auth_token_encryption_at_rest` (rolled out in batches, Windows and macOS alike), rewrites `cursorAuth/accessToken` and `refreshToken` as `cursor-safe-storage:<version>:<base64>` on its next start. Sent as a cookie that is a certain 401, and 0.14.6 then told the user to sign in again, which only writes the same ciphertext. Now a token starting with `cursor-safe-storage:` (the whole prefix family, not just `v1`) makes `parse()` return `skipped: true` with one warning, no request and **no `info`**: `sync.js` prunes no Cursor key and keeps `parserMeta.cursor` (`syncedAt`, `backfill`) as recorded, so once a readable token is back `planBackfill()` refills the paused weeks like any gap. The warning prints on every run (parser warnings are never filtered), names the issue, says other tools keep syncing and that signing in again does not help, and carries nothing from the token. Neither desktop app shows stderr of a successful run, so it reaches CLI users and log files only. `status` (which runs no parser) prints the same notice in place of its 48-hour "check the signed-in account" hint when the newest recorded event is stale and `localCursorTokenEncrypted()` — `parse()`'s own token read reduced to a yes/no, called only then — says the local token is encrypted; neither desktop app runs `status`. The decision is **no local decryption**: do not read Cursor's `Local State`, call DPAPI, or touch the Keychain / libsecret. A decrypting reader, or the separately connected Cursor account the maintainer may add later (observing first), changes credential policy and passes the Architecture Approval Gate before any code. Coverage: `test/cursor.test.js` (prefix family, zero requests, no info, message), `test/cursor-rolling.test.js` (an encrypted run keeps state and progress; the readable token afterwards refills the gap) and `test/cli.test.js` (`status` with an encrypted vs. readable token).

Codex forked sessions (`codex.js`):
- Forking a Codex conversation writes a *new* rollout file that replays the entire source conversation at the top — every `event_msg/token_count` included, all timestamped in a 1–3s burst at the fork instant. Those tokens are already counted from the source session's own file, so naively parsing the fork double-counts and spikes token/cost at the fork timestamp.
- Unique ordinary sessions take a cheap header discovery pass followed by one usage pass. Only forks, sub-agents, their referenced parents, corrupt headers, and duplicate session ids build the full replay index. For those files, the index treats only the first `session_meta` as canonical and records a monotonic raw-`token_count` timestamp plus compact payload fingerprint. The usage pass skips the longest child token prefix that exactly matches a suffix of the parent snapshot present at spawn. Requiring the snapshot suffix avoids false matches against unrelated interior turns, remains exact when the parent continues running, and avoids over-skipping truncated-history forks. Recognized sub-agents have one additional live-write safeguard: when their exact leading payload sequence matches an interior parent slice but has not reached the snapshot suffix yet, that sequence is treated as an in-progress replay instead of real usage. If the source file is missing or no payload sequence matches, skip nothing unless the child provides its own task boundary.
- All raw-log passes **stream** each rollout line-by-line (`node:readline` over a `createReadStream`). Same-ID continuation groups retain an in-memory graph of fingerprints and allow-listed accounting/timing fields while merging; chat/tool payloads are hashed transiently and never retained in the graph or cache. Every read is bounded to the size captured before parsing. Exact stat signatures reuse cached summaries with zero raw-log reads. Ordinary append-only files additionally validate inode/device, size growth, newline alignment, and a trailing-prefix guard before reading only the new bytes; complex replay participants and any failed guard take the complete path. A 30-day rolling audit re-reads at most one warm file or continuation group up to 64 MiB total per invocation. Non-interactive cold builds use a 45-second work budget (105s let the other parsers and the upload run past the apps' 120s wall during the 0.14.8 rebuild) and return `skipped` progress so `sync.js` protects old upload state while the next run resumes from per-file checkpoints. A parser-algorithm bump must not discard every entry (0.14.8 did, and large histories stopped uploading), so keep bumps rare and keep reading what is still exact: algorithm 6 (#143) only added raw Magpie attribution fields, and algorithm-5 entries stay valid while the sync's Magpie context has no ledger, no cut and no read failure (`magpieFree` in `codex-cache.js`), because attribution is then a no-op; machines where Magpie is active rebuild. Algorithm 7 (2026-11-18) keeps Ultrafast usage apart (`result.ultrafastBuckets`, raw model name) and names it from the machine's cut after cache assembly; an older summary folds it into the plain model, which is still exact for every window before the cut, so `summaryMatchesCut()` re-reads only rollouts with a window at or after it. Older tails are never resumed. An older entry without a usable summary still gives its header and replay index, which depend on neither the tier nor the cut — but only from the versions listed in `SAME_HEADER_AND_INDEX_ALGORITHM_VERSIONS` (`codex-cache.js`), which compute them exactly as the current one. **Empty that set whenever the output of `readSessionHeader()` or `indexSessionFile()` changes, including through `normalizeUsageRecord()`**; a header or index from a different computation would be trusted silently (a wrong replay boundary double-counts a fork's copied history). This matters most for sessions that exist in several homes: their physical files never have a summary of their own, only the group does. **A new algorithm version gets its own directory and treats older versions' files as read-only** — collectors of two versions run side by side for days after every release, and a shared file is a file they fight over. See the 2026-11-18 approval above.

Codex sub-agent sessions (`codex.js`):
- A sub-agent rollout (`session_meta.payload.thread_source === 'subagent'`, a `source: { subagent: ... }` object, or a `parent_thread_id`) can begin with full parent history (including a second parent `session_meta`) or a last-N-turn suffix without that meta. Only the first child meta is canonical. The exact token-sequence match locates the copied suffix; the child's own `task_started`/`turn_started` at the end of that suffix supplies the record boundary so copied timing events are skipped too. If a live rollout currently contains only an exact partial copy of the parent, skip that matching prefix until a later stable snapshot reveals the completed replay boundary. Legacy single-meta files fall back conservatively to their first task boundary, and unmatched payloads retain fail-open counting.
- Duplicate `token_count` emissions: Codex occasionally writes the same record twice back-to-back — identical `last_token_usage`, unchanged `total_token_usage.total_tokens`. A real API call always advances the cumulative counter, so an unchanged **positive** total marks the event as contributing zero (duplicate, or zero-usage bookkeeping like compaction) and it is skipped instead of summing `last_token_usage` twice. Guarded to positive totals so builds that leave `total_token_usage` all-zero can't suppress real usage.

DeepSeek Harness parser (`dsh.js`):
- Session logs at `$DSH_HOME/sessions/<project-key>/<id>/session[.vN].jsonl[.zstd]` (default `~/.dsh`; fixture/relocation override `VIBE_USAGE_DSH_SESSIONS`) support released formats V0–V4, checked against DSH tag `dsh-v0.1.5-alpha.2` plus the V4 integration format (commit `669b724a78`, `docs/persistence-changes/2026-09-16-session-format-v4.md`). V4 keeps the filename, header fields, assistant usage block, and inherited cut; it lifts user-role tool results into tool-role messages, adds `forked` to `turn/end.reason`, and adds `developer/message`, none of which carry billable usage. Select the highest canonical generation per session directory; never fall back to a frozen predecessor on a corrupt, unreadable, mismatched, or unsupported current generation. Across copied project directories, prefer the newest format before comparing same-version decompressed sizes. DSH migrations retain the original files and can shrink newer logs, so reading every generation double-counts and choosing by size can freeze updates.
- Compressed logs are multi-frame Zstandard — one frame per write batch. Node's `node:zlib` zstd (Node ≥ 22.15) decodes exactly one frame per call, so `splitZstdFrames()` walks the RFC 8878 frame structure (magic/header/blocks/checksum, skippable frames) and decompresses each standard frame separately; an incomplete final frame is ignored at the last complete boundary, while invalid complete structure fails the source as `skipped`. Older Node uses `zstd -d -c`. Probe `zstd` on `PATH` first, then `/opt/homebrew/bin/zstd` and `/usr/local/bin/zstd` on macOS. If neither decoder works, the parser returns `skipped` with a hint to preserve prior state. Plain JSONL logs are read directly.
- Usage comes from `assistant/message` records. `usage.inputTokens` is uncached input; optional `usage.cacheWriteTokens` is folded into `inputTokens` because the shared bucket schema has no cache-write column; `usage.cacheReadTokens` maps to `cachedInputTokens`. `usage.outputTokens` includes `reasoningTokens` (verified against DSH's own `session_projcache` totals), so reasoning is subtracted from output into `reasoningOutputTokens`.
- Replay dedup is version-specific. V0/V1 use header `parentSession` + numeric `seedLength`; their untagged `session/end-seed` markers may appear after real history and must never define the cut. V2–V4 require boolean `isSeeded`; a seeded log uses the LAST marker whose `data.inherited === true` (its seq excludes the marker itself). An untagged resume marker cannot extend that cut. Reject inconsistent modern seed metadata with `skipped` so upload state survives. Below the cut, skip only messages confirmed in the parent by seq, role, model, and token accounting. Mixed-format migrations renumber seqs, so require preserved message ids in order instead of matching seqs across versions. Ids remain parser-local; session/upload identities do not change. Missing or divergent parent copies retain the sole local history.
- Timing events: `user/message` records with `source.kind === 'user'` (plugin-sourced messages are ignored) plus every `assistant/message`; only sessions with a real user prompt reach `extractSessions()`.
- DeepSeek Harness is in developer preview with compatibility-breaking changes expected. `MAX_SESSION_FORMAT_VERSION` gates both filename and header versions; require those versions to agree. Unknown canonical filenames must warn even if an old supported generation remains alongside them. Before extending support, inspect the upstream filename convention, header, assistant usage, and inheritance codec rather than merely increasing the version limit.

Codex archived sessions (`codex.js`, `tools.js`):
- Codex moves a "completed" session's rollout file from `$CODEX_HOME/sessions/` to `$CODEX_HOME/archived_sessions/` (default `~/.codex`, override honored via `CODEX_HOME` like the Codex CLI itself — also the test hook). The parser scans **both** dirs in one pass (`sessionsDirs()`); scanning only the live dir permanently lost any session archived between two syncs. A newly moved path may be parsed once before receiving its own cache entry; complete outputs and server-side upserts remain idempotent, and indexing both dirs together keeps fork replay-skip correct when a fork and its parent are split across them.
- Files sharing the first session id may be distinct continuation segments. Merge their unique records before computing usage, timing, and fork replay boundaries; suppress exact cross-file copies by full-record fingerprint plus per-file occurrence number, preserving repetitions within a file and each file’s record order. Token records retain their segment-local model/tier context. Conflicting copy order or a failed group read skips Codex, protecting prior upload state. Each group has a disposable cache keyed by every member path/stat signature (except proven compressed copies, see below); any append, replacement, move, addition, or removal invalidates it. Members with the same bytes (hard links; proven compressed copies) are read once (`planCodexSegments()`), and a group that is neither a fork nor a sub-agent is summarized right after its merge, so a build that runs out of budget before the usage pass does not merge it again. Session/upload identities are unchanged, and corrected same-key totals are upserted without reset or migration. `findCodexDataDirs` in `tools.js` likewise treats either dir as "Codex installed".

Codex compressed rollouts (`codex.js`, `zstd-file.js`; issue [#168](https://github.com/vibe-cafe/vibe-usage/issues/168), 2026-11-18):
- Codex Desktop compresses every rollout untouched for 7 days to `<name>.jsonl.zst` at startup and deletes the plain file (`codex-rs/rollout/src/compression.rs`, `MIN_ROLLOUT_AGE`); reopening the conversation restores the plain `.jsonl` and deletes the `.zst` (`materialize_rollout_for_append`). Both directions write a temporary file, publish it, then delete the other form, so both forms exist only for a moment, with the same records (the restored plain file possibly with more appended). Codex reads the plain file and skips the compressed sibling (`should_skip_compressed_sibling`); `findRolloutFiles()` does the same, and `statRollout()` takes the other form when the listed one disappeared between the listing and the stat. Until this release the parser read `.jsonl` only, so every conversation older than a week was invisible (3950 of 4204 rollouts on the maintainer's Mac on 2026-11-18): a `reset`, new account or new machine lost that Codex history, and a fork or sub-agent whose parent was compressed counted the copied parent history a second time.
- `zstd-file.js` reads the file as a stream (never to disk, never whole: single rollouts reach 2.5 GB compressed / 3.5 GB decompressed). It locates each frame from its headers and decodes it with its own `zlib.createZstdDecompress()`, then requires the declared content size. Node's decoder cannot be trusted with the structure: on Node 22 (22.19 measured; the Windows app bundles 22.23.1) both the one-shot and the stream decoder stop after the first frame and decode a truncated frame to its complete blocks, all without an error; Node 24 (the Mac app's 24.22.3) does neither. Codex writes one frame per file with its content size and no checksum (all 3950 local files), so multi-frame input is supported but not seen in practice. Never shell out to a `zstd` binary.
- Without `node:zlib` zstd (Node before 22.15 — the `engines` floor is 20, both desktop apps bundle newer), compressed rollouts are left unread exactly as before and the parser adds one `decoder_unavailable` warning per run naming how many; the rest of Codex still syncs. Skipping the source instead would stop all Codex uploads for those users, who were syncing their recent usage. A compressed file that does not decode (bad structure, size mismatch, decoder error) skips the whole Codex source with a warning naming the file (`unsupported_format`) in whichever pass finds it — header, replay index, segment merge or usage — and is never counted in part or dropped silently (dropping a parent would bring back the fork double count). Codex verifies a compressed file before publishing it, so this means damage on disk and repeats every sync until the file is repaired or removed.
- A rollout that is gone by the time its replay index is read (`ENOENT` after its header was read: Codex compressed, restored or archived it during the sync) skips Codex for that run (`read_failed`); the next run finds it under its new name. It used to be dropped silently, which made a fork of it count the copied parent history again — permanently, since the server keeps the larger value. Found in cross-review (GPT-6.1-Sol, 2026-11-18); it predates compression (archive moves), compression and restore make it routine. Other index read errors on a default home still drop just that file, as before.
- A compressed rollout is summarized only as a whole file: no append tail is captured or resumed (compressed offsets are not text offsets, and Codex never appends to a `.zst`), and its cache entry is keyed by its own path and stat signature like any rollout. Compressing or restoring a file therefore re-reads it once under its new name; no entry changes meaning, so `CODEX_PARSER_ALGORITHM_VERSION` stays 7 and older entries stay valid. The summary records `decodedBytes`, which bounds the rolling audit instead of the file size; a continuation group with a compressed member is not audited. A rollout without a session id keeps its plain path as the session key.
- Leaving a `for await` over a `readline` interface early does not close it: the input keeps flowing to its end in the background. `readSessionHeader()` used to read every plain rollout in full that way, and for a compressed one it would decompress the whole file and turn damage past the header into an uncaught exception. Callers that stop early must `close()` the interface; `readLines()` then destroys the input and swallows its late errors.
- Copies shared between homes (2026-11-19, before 0.15.1 shipped): Orca keeps one Codex home per account (`~/Library/Application Support/orca/codex-accounts/<id>/home`, configured as `extraRoots.codex`) and hard-links each rollout into them; Codex Desktop, run on `~/.codex`, compresses its own copy to `.jsonl.zst` while the plain links in the Orca homes stay as they were. On the maintainer's Mac 3705 of the 3714 sessions whose `~/.codex` copy is compressed have a plain copy of exactly its decompressed size, and every pair of plain copies is one inode. Reading `.jsonl.zst` added that copy to each such session's continuation group, which changed the group's cache key, so every group was merged again from all its copies, and merged a second time in the usage pass of a later run because the duplicate-id loop kept only the index: 31 non-interactive runs on that machine. Now (all exact, nothing is assumed from sizes or names): (1) a compressed rollout of a duplicated session is compared byte for byte (`zstdFileCopyOf()`) with the plain copy its group sorts first among those of its decompressed size before its replay index is built; equal bytes take that copy's index (plain rollouts are indexed first) and record `copyOf` (the plain copy's path and stat signature) in its own cache entry, trusted only while both signatures are unchanged. A hard link (same stat signature) takes its twin's index without a read. (2) `planCodexSegments()` puts members with the same bytes in one class and merges one member per class, a plain one where possible: a later member of a class adds no record and no order to the merge. The group's cache entry is named by its members without the proven compressed copies whenever that leaves the same sequence of classes (equal sequences merge identically), so the copy leaves the entry where it was: the summary of the plain links stays valid, including one written by an older release. (3) A merge of a single class skips the record graph, which for one file is its records in order. (4) A group that is neither a fork nor a sub-agent is summarized right after its merge (its replay boundary does not depend on any other session). (5) A header read of a compressed rollout decodes only the start (`zstdFileHeadChunks()`) instead of first walking every block header, which on a cold disk reads the whole file; the full read later still walks and checks every frame. Coverage: `test/codex-shared-copies.test.js`.
- The first sync after an upgrade must upload Codex (2026-11-19, the maintainer's rule: a `skipped` first sync blocks the release). Reading years of compressed history takes several 45 s runs on a heavy user's machine, so once every header is read (discovery still returns `skipped` when it cannot finish: an unknown header could be a copy or a parent of any session) a run that runs out of budget no longer skips the source. It uploads every session it can compute exactly and leaves for a later run each session that depends on what it has not read: a rollout without its replay index or usage yet, a group with such a member or not merged yet, and a fork or sub-agent whose parent session is still waiting (without the parent the copied history would count). The result carries `indexing` (phase, rollouts done / all) and `skipped` stays unset. Leaving a session out only delays it: the server keeps the larger of two values for one key, so a window that is temporarily low changes nothing there, while an excess would be permanent. `sync.js` does not prune the upload state of a source that reports `indexing`, as for `skipped`, so what waits is not re-sent once it is read. Reading compressed history no run has read yet (index, merge or usage involving a `.jsonl.zst` without a cache entry) only starts within `BACKLOG_SHARE` (two thirds) of the budget; the rest stays for the plain rollouts that changed, so the conversations in use are uploaded in the same run. Groups merged from plain files only are processed first. Coverage: `test/codex-partial.test.js` (simulated clock).
- Re-upload: the first sync with this release finds every compressed conversation again; their keys were pruned from `state.json` while they were invisible, so they are sent once more. The server keeps the larger of two values for one key and never sums, so a key that was uploaded when the file was plain is not counted twice. A new key would be — that needs a naming rule that changed after the file was last uploaded as plain: the service-tier suffix (fixed start 2026-08-31, first shipped in 0.10.18 on 2026-08-30) on a machine that never ran 0.10.18+ before its files were compressed; the Windows backslash project fix (0.14.1) on a CLI-only Windows machine; or an `uploadProject` change after the compression. Every such rule predates mid-November, when compression reached users, so a machine that kept updating is not affected. Not corrected automatically: what a fork already uploaded twice while its parent was compressed (the corrected, smaller value is refused by the server's regression guard; only `reset` with this release fixes it).

## Versioning

- Keep `version` aligned in `package.json` and `package-lock.json` before publishing
  (`npm version <x.y.z> --no-git-tag-version` updates both; hand-editing one is how they drift)
- Published as `@vibe-cafe/vibe-usage` on npm
- Users run via `npx @vibe-cafe/vibe-usage`
- **Release entry point: `scripts/release.sh`** — run it from a real terminal, never behind a pipe. `scripts/release.sh --dry-run` runs every preflight and stops before publishing; `scripts/release.sh [<expected-version>]` publishes the version in `package.json`, asserting it equals the argument when one is given. It mechanises the rules in this section and the next: main branch, clean tree, `--ff-only` pull, `package.json`/`package-lock.json` version agreement, the version not already on the registry (`npm view --prefer-online` — the cached form reports the *previous* release), a green `node --test`, a logged-in npm, `script(1)` instead of a pipe so passkey 2FA still opens a browser, and post-publish verification by unpacking the published tarball and running `npx` from a temporary directory. The prose below is *why* each check exists — read it before weakening one. The script is not shipped to npm (`files` is `bin/` + `src/`). Verified through the login check on a machine with no npm credentials. 0.14.6 (2026-11-07) went through the publish step, but the registry took about 5.5 minutes to show it and the script, then waiting only 150s, stopped there as a failure; it now polls up to ~10 minutes, and on timeout exits 3 with instructions to confirm (`PUT … 202` in the logs, `npm view --prefer-online` later) instead of re-publishing. The tarball and `npx` checks after it have not been exercised end-to-end.

### Publishing with 2FA on the account

**Do not pipe `npm publish`.** With webauthn/passkey 2FA the CLI opens a browser and
polls for approval, but it only does that when stdout is a TTY. Behind a pipe it skips
the browser step and fails `EOTP` instead — asking for a code the account does not have.
Three releases were burned on this before the pipe itself was suspected; the wrapper
added *to observe the failure* was the failure.

```bash
# Wrong: tee makes stdout a pipe, npm never opens the browser
npm publish --access public 2>&1 | tee publish.log

# Right: script(1) keeps a pty and still captures everything
script -q publish.log npm publish --access public
```

- **`EOTP`'s wording lies.** "requires a one-time password from your authenticator" is a
  generic message; it does not mean a TOTP app is enrolled. Ask which second factor the
  account actually has instead of inferring one from the error, and do not reach for
  `--otp=` on a passkey-only account.
- **`npm whoami` returning a username is not proof you can publish.** A stored token
  authenticates the account without satisfying 2FA, and the EOTP lands *after* npm has
  packed the tarball, so it reads like a packaging failure.
- **`npm login --auth-type=web` can fail on its own.** Its `/-/v1/login` endpoint has
  returned `ECONNRESET` while `publish` reached the registry fine in the same minute —
  and when it fails **no browser opens at all**, which looks like the human forgot to
  click. A login failure says nothing about registry reachability.
- **A successful publish is async: `PUT 202` + "Your package is being processed".**
  `npm view` and the version endpoint (`/<pkg>/<version>` → 404) keep showing the old
  release for a few minutes (about 5.5 for 0.14.6). Exit code 0 with `info ok` in `~/.npm/_logs/` is the real
  signal; a `202` is acceptance, not failure.
- **Those log filenames are UTC** (`2026-09-09T17_16_54_269Z`). Convert before deciding a
  log is stale — a success two minutes old reads as eight hours old at UTC+8.
- **Verify by unpacking what was published**, never by the exit code alone:
  `npm pack @vibe-cafe/vibe-usage@<version> --prefer-online`, untar, grep the shipped
  `src/`. `npm view` without `--prefer-online` reads a local cache and reports the
  previous version as current.
